ERROR HANDLING & PARTIAL FAILURES

If any step fails:
    ┌─────────────────────────────────────────────────────────────┐
    │ Step fails → Error logged                                   │
    │                                                             │
    │ If CRITICAL (Lookup, DB Transaction):                      │
    │   → Abort immediately                                      │
    │   → Item remains unchanged                                 │
    │   → Return error to user                                   │
    │                                                             │
    │ If NON-CRITICAL (Gemini, S3 warnings):                     │
    │   → Continue with next steps                               │
    │   → Log warning                                            │
    │   → DB still updated (item marked as deleted)              │
    │   → Return partial success                                 │
    └─────────────────────────────────────────────────────────────┘

Example: S3 down, but Gemini works
    → Gemini files deleted ✓
    → S3 deletion fails ⚠️
    → DB marked as deleted ✓
    → Result: "Partial success, retry S3 cleanup"

PARENT-CHILD WEBSITE DELETION (Important!)

When you delete a PARENT website:

    Website Tree:                  Deletion Order:
    ┌─ Parent (ID: 98765)          1. Lock parent row
    ├─ Child 1 (ID: 98766)     →   2. Fetch all children
    ├─ Child 2 (ID: 98767)     →   3. Revoke parent + all children tasks
    └─ Child 3 (ID: 98768)     →   4. Delete from Gemini (all docs)
                               →   5. Delete from S3 (all files)
                               →   6. ATOMIC: Delete parent + children together

    Database Transaction:
    BEGIN;
        DELETE FROM scraped_websites WHERE id = 98765;
        DELETE FROM scraped_websites WHERE parent_id = 98765;
    COMMIT;  ← All or nothing

When you delete a CHILD page only:

    Only that child deleted:
    └─ Child 2 (ID: 98767)
       - Celery task revoked
       - Gemini doc deleted
       - S3 files deleted
       - DB record deleted/marked

    Parent and other children: UNCHANGED ✓

PERFORMANCE & TIMING

File Deletion:                  Website Deletion:
├─ Lookup: 10-50ms            ├─ Lookup (parent): 10-50ms
├─ Celery: 100-200ms          ├─ Lookup (children): 50-200ms
├─ Redis: 10-20ms             ├─ Celery (all tasks): 200-500ms
├─ Gemini: 500-2000ms         ├─ Redis (all tasks): 50-100ms
├─ S3: 200-500ms              ├─ Gemini (all docs): 1000-5000ms
├─ DB: 50-100ms               ├─ S3 (all files): 500-2000ms
└─ Total: ~2-5 seconds        └─ Total: ~3-15 seconds (depends on page count)

Bottleneck: Gemini FileSearch deletion (1-2s per document)
Optimization: Parallel S3 deletes, batch Gemini operations (if API supports)

DATA GUARANTEES AFTER DELETION

Soft Delete (Default):           Hard Delete (Complete Removal):
├─ ✓ Removed from all APIs       ├─ ✓ Everything from soft delete
├─ ✓ Not searchable              ├─ ✓ Row deleted from database
├─ ✓ No Gemini access            ├─ ✓ No audit trail
├─ ✓ No S3 access                ├─ ✓ Completely gone forever
├─ ✓ Celery task killed          └─ Use for: Right-to-be-forgotten
├─ ✓ Record in DB (audit trail)     (GDPR, explicit requests)
└─ Use for: Normal deletions,
   maintaining audit history
